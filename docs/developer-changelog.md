# Developer changelog

Changes that matter to people working on the add-on rather than using it: the
TactileDisplayAPI COM layer and its vtable history, the build and release
machinery, and the presentation framework.

These entries are kept out of [`CHANGELOG.md`](../CHANGELOG.md) because that
file's `[Unreleased]` section is published verbatim in every dev and beta release
body (see [`releasing.md`](releasing.md)), where this detail would bury the
user-facing changes.

- Ruff's logging checks (`G`) are enabled, and the add-on's logging conventions are written up in [`docs/logging.md`](docs/logging.md).
- Per-commit builds are versioned `0.0.<run_number>` instead of the git sha. NVDA parses an add-on version as 2-3 dot-separated integers, so a sha did not parse at all and every automatic build was mutually incomparable. The reserved `0.0.x` band keeps them below any release, unlike a date-derived version, which would outrank `1.0.0` permanently. `lastTestedNVDAVersion` drops to `2026.1.1`: the store forces a submission naming an experimental API version onto `beta`/`dev`, and 2026.2 is still flagged experimental. Both 2026.2 and 2026.3 declare `backCompatTo` 2026.1.0, so compatibility on those releases is unaffected. The scheme, the `.9x` pre-release band and the store's submission constraints are written up in [`docs/releasing.md`](docs/releasing.md).
- `manualRelease.yaml` takes a `releaseType` (`dev`/`beta`/`stable`) instead of a bare `prerelease` boolean, and rejects a version NVDA cannot parse (2-3 dot-separated integers) and any release in the reserved `0.0.x` band, all before anything is built, committed, tagged or published. Only a stable carries its version in `pyproject.toml`, which holds the one authoritative version line; dev and beta cuts carry their version in the tag and release, which keeps the branch from being stamped with an already-published pre-release number and avoids a version-bump commit for every test build. For a stable the workflow rewrites `pyproject.toml` and the root version in `uv.lock` — the lock records the root project's own version and the build runs `uv sync --locked`, which refuses a lock that disagrees, so bumping one without the other aborted every stable cut before it packaged anything — then commits only if that changed anything. Job-level `continue-on-error` is gone — it would have turned these guards green on failure.
- Manual releases compose their own notes: a compare link against the previous numbered release, and — for dev and beta, which never get a `CHANGELOG.md` section of their own — the `[Unreleased]` section collapsed behind a `<details>` block, above GitHub's generated list of merged PRs. That generated list is pinned to the previous numbered tag, because GitHub otherwise picks the most recent one, which is normally the per-commit workflow's moving `latest`. Checkout is now full-depth so those tags are visible.
- `tests/test_releaseMetadata.py` fails the build when the store's what's-new text (`buildVars.addon_changelog`) is *older* than the project version — the state that let it announce "New in version 0.2" for as long as the version sat at 0.2.0 — or when `CHANGELOG.md` has lost the `[Unreleased]` section a release depends on renaming. It is a check rather than generation because `_` is an identity marker and xgettext extracts by scanning the source, so the text has to stay a literal to remain translatable. [`.claude/commands/cut-a-release.md`](.claude/commands/cut-a-release.md) is the accompanying procedure.
- Disconnecting a display over Bluetooth no longer clears it packet by packet first. The display clears itself once it notices the link has gone, and the scheduled disconnect causes exactly that, so the clear was one packet per external row -- each waited on, on NVDA's main thread -- for no visible effect. It is kept for serial, where the device cannot tell the host has closed the port while the cable is still connected. `_isBleConnection` records the transport at connect time and also replaces the `getattr(self._dev, "isConnected", ...)` duck-typing in `_isDeviceConnected()`. Note the skip relies on firmware behaviour the Dot protocol specification does not describe.
- `terminate()` step 6 no longer joins the packet sender unbounded, and a timeout during termination no longer latches `_displayGone`. #147 bounded the queue drain at step 5 but left the join, so the same main-thread freeze was reachable one step later -- the sender can be parked in `self._dev.write()`, which has no timeout of its own. Separately, `_sendQueuedPacket` latched `_displayGone` whenever `_waitForSendSlot()` expired and `_isTerminating` was not yet set, which is the whole termination drain: with `TERMINATE_ACK_TIMEOUT_SECONDS` at 1.0s against a normal full-area render of several seconds, that discarded every remaining clear packet on healthy hardware, at every termination.
- `Ble.close()` no longer waits without a bound. It is called from `terminate()`'s `finally`, which runs on NVDA's main thread, so `_queuedData.join()` and `_readerThread.join()` are now bounded by `CLOSE_TIMEOUT_SECONDS`. That matters more since the sender thread's join became bounded: the sender can still hold `_ackLock` while the reader blocks on it dispatching a packet, so waiting on the reader could deadlock on a thread termination deliberately stopped waiting for. The disconnect is the exception -- it is scheduled with `runCoroutine` rather than awaited, because cancelling it would not stop the WinRT operation already in flight and the client is about to be dropped, which could leave the peripheral connected with nothing able to close it. Bounded waiting, unbounded operation.
- The ini patcher's dev-mode guard resolves the add-on path before looking for `.git`. A dev install is usually a symlink from NVDA's addons directory into the working copy, and `__file__` keeps the path a module was loaded through -- so the guard walked NVDA's configuration directory, found no `.git`, and the patcher rewrote all 27 tracked locale inis on every NVDA start. That is how a developer machine's `LiblouisPath` reached the repository once already. The new test links through a directory junction when `os.symlink` is unavailable, since it needs privilege on Windows and a skipped test would prove nothing about the case the guard exists for.
- `tools/generateLibraryInis.py` forces a small table of `[Settings]` keys (`SETTINGS_OVERRIDES`) into every generated locale, replacing the value when the vendor reference carries the key and appending it when it does not. v1.0.36 exposed `EquationShowLabel` and `SuppressHybridBraille` as ini switches rather than as new vtable slots, and both address the same mismatch: the addon hands the library zero text cells (NVDA keeps the 20-cell line to itself, see `simulatedDisplay.computeSimulateDisplayArgs`), so the library concludes there is no separate display and falls back to painting the equation label and the braille line onto the tactile area — over the graphic, and duplicating what NVDA is already showing. The values live in the generator rather than hand-edited into `enu/TactileDisplayAPI.ini` because that file doubles as the generator's vendor reference: the next drop overwrites it, and a hand-edit would be silently lost.
- `tools/generateLibraryInis.py` no longer takes the ini wire encoding from the vendor reference. That reference is pure ASCII, so its encoding says nothing about what the library's reader accepts — and v1.0.34 shipped it as plain UTF-8 after six releases of UTF-16 LE + BOM, which would have silently re-encoded all 27 locales into the pre-v1.19 format that truncates U+2800–U+28FF. For languages whose NVDA abbreviations are themselves Unicode braille (Russian has them for nearly every key) that is every control-type and state label on the multi-line area. `resolve_output_encoding` derives the format from `LIBRARY_SUPPORTS_UNICODE_BRAILLE_IN_INI` instead, mirroring the reference only when that gate is off. `--dry-run` compared decoded text, which is why the regression was invisible — same text, different bytes, reported as no change — so `is_unchanged` now also requires the on-disk encoding to match.
- The packet sender's acknowledgement gate is a `threading.Event` rather than a bool polled every 10 ms. The old wait was unbounded, so a display that stopped acknowledging blocked the sender thread forever -- and with it `terminate()`, which joins that thread. NVDA core's own acknowledgement timer (`_ackTimeoutResetter`) only resets core's `_awaitingAck`; it never released this gate. The wait is now bounded (see the render budget entry below), and on expiry either retries via `_resendLastPacket` (which was dead code -- nothing called it) or hands the display back to NVDA. `handleDisplayUnavailable()` terminates the driver and termination joins the sender thread, so it is dispatched with `core.callLater` to avoid deadlocking on itself. When the display is gone the thread keeps draining the queue instead of exiting, because `terminate()` joins the packet queue before signalling the thread.
- Sending a packet is now guarded, and `task_done()` moved to a single `finally` in the sender loop. `self._dev.write()` was unguarded, so a serial write failure (an unplugged cable raises `OSError`) escaped `_queuedPacketsSender` and killed the thread, after which nothing consumed the queue and `terminate()` blocked on `_queuedPackets.join()`. A write failure is now the transport-agnostic signal that the display is unreachable -- which is the only one serial has, since `hwIo.Serial` exposes no `isConnected()`. The per-packet work moved into `_sendQueuedPacket()` so no exit path can leave an item unconsumed.
- `_librarySetupPending` distinguishes "the library has not finished starting" from "the library is unavailable", so only the latter is announced. The driver starts its reader threads before `_setupLibrarySingleton()` completes, so a render can arrive mid-startup; the window is only observable when `__init__` runs off the main thread, which is why it appeared on automatic detection but not on manual selection. Cleared in a `finally`, so a setup that genuinely fails is still announced. The next update picks up the library, so only the first write is NVDA-rendered.
- `Detector.matches()` yields nothing when called with `bluetooth=False`, instead of stopping the scanner and then reporting its cached results anyway. NVDA uses that scan to look for a USB display while one is already connected over Bluetooth; reporting the connected BLE device there made NVDA reconnect to it, which triggered another such scan, which reported it again -- a reconnect every few seconds, with the driver never living long enough for the TactileDisplayAPI library to finish starting. Only reachable once the `provider` key above made NVDA use that scan at all.
- BLE device matches now report `deviceInfo["provider"] = "bluetooth"`. NVDA only keeps a USB-only detector running for the current driver when the connected match looks like Bluetooth; without the key it took the wired branch and called `_disableDetection()`, so auto-detection stopped entirely for the rest of the session. The value is deliberately not `"ble"`: released NVDA compares against `CommunicationType`, which gains a `BLE` member only with nvaccess/nvda#19122, and that PR widens the check to accept both. `DeviceMatch.type` is unchanged -- it identifies saved ports as `f"{match.type}_{match.id}"` in the user's configuration and selects the transport in the driver.
- `terminate()` no longer blocks the main thread. It ran `Queue.join()` (which has no timeout) before signalling the sender, so a display that had stopped responding held the main thread for the whole escalation budget -- NVDA's watchdog reports a freeze after 25s, and hardware logs showed exactly that, four times. A `_terminationStarted` event is now set first, so the sender stops waiting out render budgets and treats the clear packets as best-effort, and the drain is bounded by `TERMINATE_DRAIN_TIMEOUT_SECONDS`.
- `MAX_CONSECUTIVE_RENDER_TIMEOUTS` drops from 6 to 2. The budget is already the device's stated maximum for refreshing the entire area, doubled, and any packet at all resets the counter, so two is two worst-case refreshes with complete silence. On hardware six cost about 43 seconds.
- The send gate's budget comes from the device's own `DisplayDescriptor.refreshTime` (100 ms units per the Dot protocol specification), not from `timeout`. The gate opens on `NTF_DISPLAY_LINE` -- pins physically moved -- not on `RSP_DISPLAY_LINE`, so a protocol-level budget would expire on healthy hardware and resend lines the display had already accepted. Link liveness is polled separately every `CONNECTION_POLL_SECONDS`, so a disconnect is still noticed quickly despite the long render budget. After `MAX_CONSECUTIVE_RENDER_TIMEOUTS` expiries with the link apparently up the display is released regardless, which is the only thing that catches a device powered off while its USB serial interface stays enumerated (writes keep succeeding, so nothing raises). The counter resets whenever any packet arrives from the display, rather than when the gate opens, since `_resendLastPacket`'s give-up branch also opens it.
- `handleDisplayUnavailable()` is only invoked if this driver is still the current display when the scheduled callback runs, so a failed probe cannot tear down the display NVDA fell back to.
- `_displayGone` resets per candidate port, so one unresponsive port no longer suppresses the probe packet for every port after it.
- BLE connect is bounded at `CONNECT_TIMEOUT_SECONDS` (5s). Windows' GATT connect against an unreachable peripheral runs for roughly 30 seconds and bleak does not bound it: its `timeout` covers only `find_device_by_address` (skipped when a `BLEDevice` is passed) and service discovery, both outside the connect itself. Cancelling does not stop Windows trying, so the client is disconnected on timeout to release the GATT session.
- `Ble.write()` awaits all MTU-sized chunks inside a single coroutine instead of one `runCoroutineSync` per chunk, collapsing N cross-thread hand-offs into one.
- Backported `hwIo.ble.Scanner.deviceDiscovered` (an `extensionPoints.Action`) onto the add-on's own `Scanner`, so both implementations expose it. `Detector.matches()` waits on that action instead of sleeping for a fixed interval after starting a scan: it returns as soon as a device a registered matcher accepts advertises, and falls back to `DISCOVERY_TIMEOUT_SECONDS` only when nothing matches. Note that `extensionPoints` holds handlers weakly, so the handler must stay referenced for as long as it is registered.
- Dropped NVDA < 2026 support: the `tactile` module backport (`addon/compat/tactile/`), the 32-bit `cp311_win32` vendor target, and the version-conditional paths for `buildVersion`/`versionInfo`, multi-line braille, `DisplayDimensions`, braille-table resolution and the 32-bit `sys.maxsize` guard are all gone.
- The add-on now defers to NVDA's own facilities where they exist:
  - **Asyncio event loop**: NVDA's shared `_asyncioEventLoop` on 2026.2+; on 2026.1 a verbatim backport of it in `addon/compat/asyncioEventLoop/`. Delete that package and the fallback branch in `addon/ble/asyncUtils.py` once the minimum reaches 2026.2.
  - **BLE**: NVDA's `hwIo.ble` on 2026.3+, the add-on's own implementation against the vendored bleak otherwise. Device detection (`addon/ble/detection.py`) stays add-on-side on every version, since `hwIo.ble` has no bdDetect integration.
  Selection is by capability rather than version number, and is deferred to first use: NVDA loads add-ons before it starts its event loop and initialises `hwIo`, so an import-time decision would see facilities that exist but are not yet running. Nothing in `addon/ble/` may therefore schedule coroutines at import time.
- Removed a redundant `waitForConnection(2000)` after the BLE constructor, which already blocks until connected and services are discovered. The parameter is in seconds, so the call was a 33 minute budget rather than the 2 seconds it read as.
- Upgraded the vendored Bleak BLE library to 3.0.2, matching the version NVDA 2026.3 bundles in core, so addon code targets one bleak API on every supported NVDA.
- Vendored dependencies: bleak and winrt are bundled in `addon/_vendor/cp313_win_amd64/` (Python 3.13, 64-bit) — the only target, since every supported NVDA uses it.
  - `addon/utils/vendor.py` provides `getVendorSubdir()` and `ensureVendorPath()` for platform detection.
  - `build_vendor.py` downloads and packages the vendored dependencies; run it with `uv run --group vendor --with pip python build_vendor.py`.
  - Byte-compiled files are excluded from the built add-on, which roughly halves the number of entries in the bundle.
- Presentation framework: modular system for rendering custom content on the DotPad tactile display.
  - Subclass `Presentation` to implement custom renderers; register with `PresentationManager` via providers.
- Chart code refactoring:
  - Split `addon/utils/data.py` into separate modules: `drawing.py`, `chart.py`, `table.py`.
  - Drawing functions now take `DpTactileGraphicsBuffer` instead of callback functions.
  - Chart classes now use NVDA's `AutoPropertyObject` pattern for cached properties.
  - `BarChart` accepts `YAxisConfig` dataclass instead of raw min/max values.
  - `Chart.draw(buffer, activeColIndex=None)` replaces `Chart.draw(func_drawDot)`.
  - Backwards compatibility maintained via `data.py` re-exports.
- Table detection in browse mode no longer walks the IA2 parent chain (several COM round-trips) on every keypress. It uses an in-memory virtual-buffer field scan instead — zero COM calls for the common not-a-table case — plus a per-keypress cache for NVDA's duplicate review events. In Firefox browse mode this cut the per-keypress cost from ~240 ms to ~5-10 ms. Distinct from the earlier Google-Docs/virtual-document table support; this is the performance rewrite of that detection path.
- Enabling Screen Capture now clears any forced view. A forced view (force braille `f1+f3`, force graphic `f2+f4`, force table `longPress(f2+f3)`) previously shadowed the toggle permanently, since a forced library-braille view stays valid as long as the library source is active.
- Library buffer overrun, resolved vendor-side: `TactileDisplayAPI.dll` is updated to a v1.0.23 rebuild fixing the `STATUS_HEAP_CORRUPTION` that full-page-heap crash-dump analysis traced to the library's own internal buffer while subscribed to UIA/MSAA events for autonomous braille rendering. The COM interface is unchanged (still v1.0.23), so this is a binary-only update. With the overrun fixed, the add-on no longer suppresses unmapped-character expansion and sizes its `GetTranslation` clamp to the library's real buffer; the event-subscription ordering mitigation stays as defence in depth.
- `GetTranslation` output is bounded by the library's real `originalOffsets` buffer rather than display geometry. The library hands back a fixed-size buffer with no length; per vendor clarification (2026-06) it allocates `4 * len(input) + 4096` ints, so the add-on clamps its output and the offsets fill to `4 * len(input) + 4095` — the largest write that stays inside the allocation. The previous bound (`graphicDisplay.numCells`) was a conservative guess that could truncate legitimate pannable content; the vendor-confirmed size sits far above liblouis' largest expansion, so it protects the buffer without affecting real translations. The now-unused display-capacity plumbing was removed from the callback server and driver.
- Library-braille crash workaround + graphics-only registration: (1) `addon/utils/braille.py::translateTextWithCursor` (the function behind the library's `GetTranslation` callback) translates with plain `louis.dotsIO`. It briefly OR-ed in `louis.noUndefinedDots` to suppress liblouis's `\xNNNN` undefined-character fallback table-independently, because the `out >> in` expansion (a single U+FFFC embedded-object placeholder → ~8 cells) overran the library's internal buffer — the intermittent `STATUS_HEAP_CORRUPTION` traced by full-page-heap dumps. With that overrun fixed vendor-side (v1.0.23) and the `GetTranslation` output now clamped to the library's real buffer size (`4 * len(input) + 4095`), the suppression has been removed, so unmapped characters render with NVDA's normal fallback again. Scoped to the library path — the NVDA-review-cursor renderer is unchanged. (2) `SimulateDisplay` is now called with `totalBrailleCellCount=0, lineCount=0` (the vendor's graphics-only opt-out): the add-on drives the physical text strip via NVDA's own braille pipeline and discards the library's braille-text channel (`renderBrailleBytes` is log-and-drop), so declaring a text area only stood up an unused pipeline. (3) The `GetTranslation` debug log now records the full input text and a trailing-space count for diagnosis.
- Demand-driven library UIA-event lifecycle: the bundled library is its own UIA client (`RegisterEvents(True)` makes it render braille autonomously via the `TactileDisplayUpdated` callback, delivered through the STA worker's message pump). `RegisterEvents(True)` is no longer enabled at driver init; instead `LibraryBraillePresentation` enables it (via new `BrailleDisplayDriver.enableLibraryUiaEvents`) only *after* its blocking bootstrap completes, and disables it (`disableLibraryUiaEvents`) on teardown. This guarantees a blocking library call (e.g. `ExecuteOperation`) never runs while UIA events are live — that combination starved the STA message pump and corrupted the library's heap, crashing NVDA at activation. Ordering is enforced by the worker's FIFO submit queue, not extra locking. (A COM-MTA worker and a two-instance split were investigated and rejected — MTA delivers no UIA events so library braille goes dark, and the split reproduces the same crash recipe — see the `libraryWorker.py` module docstring.)
- Simplified the library-braille bootstrap to a single library call: the text-mode switch (`ExecuteOperation(SHOW_OBJECT_AT_CURSOR_AS_BRAILLE)`) alone renders the initially-focused control. The earlier `ShowMultilineText` warm-up (a workaround for zero-content frames in an older library version) and the explicit `AddFocusedControl` kick-start were both dropped after hardware testing.
- `LibraryWorker` diagnostics for library hangs: the worker tracks its in-flight operation (name + start time) and a completed-operation count, and `captureDiagnostics()` dumps the worker thread's live Python stack so a stuck library call is diagnosable from the NVDA log alone (no py-spy / minidump needed). On a per-call timeout, the worker still being stuck on that operation is logged at `WARNING` (visible at NVDA's default log level) with the worker stack emitted at `DEBUG`; a timeout where the worker has already moved on is logged at `debugWarning` as transient slowness. Verbose diagnostics use NVDA's existing log level — no bespoke config flag.
- Per-language TactileDisplayAPI inis: a maintainer-run script at `tools/generateLibraryInis.py` regenerates `addon/tactileDisplayAPI/<libLcid>/TactileDisplayAPI.ini` for every NVDA-supported language whose translations exist in NVDA's `.po` files, using NVDA's own `braille.roleLabels` / `positiveStateLabels` / `negativeStateLabels` for consistent abbreviations across the addon and the rest of NVDA's braille output. The existing `enu/` is overwritten by the script; 26 additional locale directories are added under `addon/tactileDisplayAPI/`. The script is idempotent (zero git diff on re-run), supports `--dry-run` for CI drift detection, and preserves all non-translatable sections (Liblouis, BrailleMarking, HID device tables, per-display keymaps) byte-for-byte from the vendor's English reference. See the script's module docstring for the re-run procedure and the `/project:update-tactiledisplayapi-library` command for the full library-update workflow.
- Upgraded bundled TactileDisplayAPI native library to **v1.21**: includes `TactileDisplayAPI.dll` and supporting natives (DotPadSDK, Mecab, TTBEngine, jsoncpp, libmathcat_c) plus the `enu/` language data, under `addon/tactileDisplayAPI/`. comtypes wraps the full v1.21 vtable (31 methods).
  - v1.21 adds hybrid print+braille mode: tactile print and braille can appear simultaneously on the DotPad's multi-line area for documents in supported applications. Activated at driver init via the new `SetHybridPrintAndBrailleMode` method.
  - v1.21 fixes events-related crashes that occurred with some application focus patterns (crashes found by Bram and others when running with UIA/MSAA event subscriptions active).
  - `ITactileDisplayAPI` gains `SetHybridPrintAndBrailleMode(flag: VARIANT_BOOL)` inserted at vtable slot 35 (mid-vtable, between `ShowBrailleOnScreen` and `EnableContractedBrailleInput`), shifting `EnableContractedBrailleInput` to slot 36 and `ExecuteOperation` to slot 37. `ITactileDisplayCallbacks` is unchanged. The new method is exposed via the `wrapper.py` Pythonic facade as `setHybridPrintAndBrailleMode`.
  - All 27 per-locale `TactileDisplayAPI.ini` files regenerated against the v1.21 vendor `enu/` reference to propagate any new keys. `tools/generateLibraryInis.py --dry-run` exits 0 after regeneration.
- Upgraded bundled TactileDisplayAPI native library to **v1.23**: comtypes wraps the full v1.23 vtable — **33 methods** (slots 7–39) after the v1.22 mid-vtable insertion. DLL and `DotPadSDK-3.0.0.dll` updated; companion DLLs (jsoncpp, Mecab, TTBEngine, libmathcat_c) unchanged. All 27 per-locale `TactileDisplayAPI.ini` files regenerated.
  - v1.22 inserted `SetBrailleLinePadding(padding: c_long)` (slot 12) and `ForceSixDotBraille(flag: VARIANT_BOOL)` (slot 13) mid-vtable between `DisplayLiteraryBraille` and what was `SetDrawingMode`, shifting every subsequent slot +2. `SetHybridPrintAndBrailleMode` moves from slot 35 → 37; `EnableContractedBrailleInput` 36 → 38; `ExecuteOperation` 37 → 39. `comInterface.py` updated with both new COMMETHODs and all renumbered slots. `wrapper.py` gains `setBrailleLinePadding` (line spacing on the multi-line tactile area: 0 = auto) and `forceSixDotBraille` (when `True`, uses 10 rows of 6-dot cells sacrificing dot rows 7/8) Pythonic facades. `ITactileDisplayCallbacks` is unchanged.
  - `MathCATRules/` restructured: braille and language rules are now zip bundles (8 under `Braille/`, 9 under `Languages/`); `Intent/` keeps loose YAML files. Old loose-YAML rules removed.
- Bundled TactileDisplayAPI native library (v1.20): includes `TactileDisplayAPI.dll` and supporting natives (DotPadSDK, Mecab, TTBEngine, jsoncpp, libmathcat_c) plus the `enu/` language data, under `addon/tactileDisplayAPI/`. comtypes wraps the full v1.18+ vtable.
  - The bundled `liblouis.dll` and `tables/` liblouis tables were **dropped** (feature 025): on every startup the addon patches each per-locale ini's `[Liblouis] LiblouisPath=` / `TablesPath=` to point at the running NVDA's own `liblouis.dll` + `louis/tables`, so the library uses NVDA's tables (a single source of truth) and the addon ships several MB smaller. `libmathcat_c` and the `MathCATRules/` tree stay bundled — NVDA ships `libmathcat_py.pyd` (Python bindings), not the C ABI the library needs, so the library keeps using its own MathCAT.
  - v1.18 appended `GetTranslation` at vtable slot 9 of `ITactileDisplayCallbacks`. The addon implements it via NVDA's `louisHelper.translate`, so the multi-line tactile area renders braille using the user's NVDA-configured translation table — the same braille NVDA's regular 20-cell display shows for the same input, including any custom or non-bundled table. The library no longer translates independently; every translation request goes through NVDA's braille pipeline. Per vendor clarification, `originalOffsets` is an OUT array (one int per output braille cell, the `brailleToRawPos` mapping) that the library uses to apply post-translation selection / typeform markers from its `[BrailleMarking]` ini config; the caller pre-allocates and we fill it in place. `cursorOffset` is INOUT despite the IDL's `[in]` annotation: the library passes the input-space cursor and we write the translated braille-space cursor back through the same pointer. Shared `translateTextWithCursor` helper lives in `addon/utils/braille.py`.
  - v1.18 ini configurability: vendor `enu/TactileDisplayAPI.ini` (and every generated per-locale ini) now exposes a `[Liblouis]` `DisplayLiteraryBraille=1` default plus optional `LiblouisPath=` / `TablesPath=` overrides for using an externally-installed `liblouis.dll`, and a new `[Mathcat]` section with `MathcatPath=` / `RulesPath=`. The generator script preserves these new keys verbatim from the vendor reference — they are not addon-managed.
  - v1.19 changed the per-locale ini wire format from 8-bit (effectively cp1252) to **UTF-16 LE with a `0xFF 0xFE` BOM** so the library can use the Win32 `GetPrivateProfileString*` family of APIs and have Unicode values survive the load path. The vendor `enu/` reference is shipped in UTF-16 LE and `tools/generateLibraryInis.py` now auto-detects the vendor's encoding from the BOM and emits each per-locale file in the same encoding. CRLF line endings are preserved (encoded as `0x0D 0x00 0x0A 0x00` in UTF-16 LE). With Unicode now surviving the load path, the generator's `LIBRARY_SUPPORTS_UNICODE_BRAILLE_IN_INI` constant is True by default — flip back to False if a future library version regresses Unicode-braille rendering of `[ControlTypes]` / `[StateFlags]` values.
  - v1.19 / v1.20 vendor fixes carried over from upstream: `ShowMultilineText` now respects paragraph boundaries (v1.18, reported by Gary at FS); MSWord heading detection now also recognises `headingLevel` annotations on enclosing elements, not just `styleID` (v1.19); the library's Liblouis loader is more robust against multiple Liblouis installations on the same machine (v1.18); fixed crashes in MathCAT and when MSWord documents end with blank paragraphs (v1.20).
  - `ITactileDisplayAPI` itself is binary-identical between v1.17 and v1.20 — the 30-method layout is unchanged; only the outbound callback interface grew by one slot at v1.18.
  - v1.17 inserted `DisplayLiteraryBraille` at vtable slot 11, between `SetBrailleTables` and what was `SetDrawingMode` in v1.16 — every slot downstream of 10 shifts +1 (ending at `ExecuteOperation` slot 36). The new method controls whether non-math text uses literary Braille (flag=1) or computer Braille (flag=0); the library auto-toggles literary on when contracted-Braille input is enabled and toggles input off when literary display is turned off. v1.18 also exposes the default via the new `[Liblouis]DisplayLiteraryBraille` ini key. The COMMETHOD is declared for vtable correctness; the addon does not yet call it and `wrapper.py` does not expose it.
  - v1.17 vendor fixes carried over from upstream: image tactilization no longer reverts to a previously-graphed math equation when the user zooms; the library's liblouis loader is harder to confuse by multiple liblouis installations on the same machine; assorted internal code cleanup.
- System COM path now uses IDispatch name-based dispatch via `DispatchProxy` (`addon/tactileDisplayAPI/dispatchProxy.py`) rather than fixed vtable slot positions. Bundled DLL version is now read at runtime from the DLL's `VS_VERSION_INFO` resource instead of hardcoded, so it no longer needs a manual update when the bundled DLL is upgraded.
- comtypes-backed COM wrapper: the TactileDisplayAPI Pythonic facade (`addon/tactileDisplayAPI/wrapper.py`) is a thin layer over a comtypes typed pointer (`ITactileDisplayAPI`). comtypes handles BSTR allocation, HRESULT auto-raise, and refcount management.
- Dedicated library worker thread: TactileDisplayAPI calls flow through an STA daemon thread with a Win32 message pump (`LibraryWorker`), keeping the library's apartment-threading model intact and preventing cross-thread COM access violations.
- SimulateDisplay caller-managed transport: the addon owns the DotPad device connection; the library is a pure rendering engine that calls back via `ITactileDisplayCallbacks` with byte buffers when content needs to be rendered. NVDA's braille driver stays attached to the device throughout — both the 20-cell text display and the multi-line tactile area operate in parallel.
- Per-driver-instance TactileDisplayAPI lifecycle: the library, worker, and callback server are constructed in `BrailleDisplayDriver.__init__` and torn down in `terminate`. Each graphic-mode interaction reuses the same long-lived worker.
- Fixed `BrailleInputOperation` Python enum (`addon/tactileDisplayAPI/comInterface.py`): v1.23 inserted `InvertLastTactileImage = 20` into the `_BrailleInputOperation` typelib between `ShowObjectAtCursorAsTactileImage` (19) and `RouteCursor`, but the Python mirror was not updated when v1.23 was bundled (feature 034). All codes from `ROUTE_CURSOR` (now 21) through `BACKSPACE_KEY` (now 35) were off by one. Operations ≥ 20 were unused in production, so no runtime behaviour changed; the fix is guarded by three regression tests in `tests/test_comInterface.py`.
- COM vtable validation tool: `tools/validateComVtable.py` detects vtable drift between `comInterface.py` and the bundled `TactileDisplayAPI.dll` before it causes access violations. Run `uv run python tools/validateComVtable.py --check` after any DLL drop-in or `comInterface.py` edit; exits 0 when in sync, 1 on count/name drift, 2 on environment error. `--scaffold` emits ready-to-paste `COMMETHOD` declarations and `wrapper.py` skeletons for newly-appeared methods, marked review-required (types are typelib best-guess; stub vs. implement still requires hardware). A baked-in allowlist suppresses the two known hand-deviations (`Connect` returns `c_int`; `GetTranslation` uses `POINTER(c_long)` with the typelib omitting the method entirely in v1.20). Companion unit tests at `tests/test_validateComVtable.py` (27 tests, pure AST/comparison layer — no DLL, no comtypes, no NVDA required). A Claude Code project command `/project:update-tactiledisplayapi-library` guides Claude through the full update workflow automatically; it covers both ZIP and EXE (InnoSetup) installer distributions, including silent extraction to a gitignored scratch directory for the latter.
- Presentation framework `triggerReason` plumbing: `Presentation.isStillValid` now accepts an optional `triggerReason: TriggerReason | None`, where `TriggerReason` is an enum (`extension_points.review_tracking.TriggerReason`) with members `CARET_MOVE` and `REVIEW_MOVE`; `None` means no discrete navigation trigger (programmatic refresh, mode toggle, initial paint). `PresentationManager.update` and `PresentationRenderer.onReviewMove` thread it through from the originating event — `ReviewTracking.handleCaretMove` emits `TriggerReason.CARET_MOVE` and `handleReviewMove` emits `TriggerReason.REVIEW_MOVE`. Presentations override `isStillValid(triggerReason)` to react to specific event types without separate event subscriptions — `GraphicPresentation` uses it to self-invalidate on caret moves so the add-on's presentation state tracks the library's autonomous braille reversion. Existing overrides that don't declare the parameter are unaffected.
